# Chat Broker — брокер сообщений между чатами и харнесами

Дата: 2026-11-06. Статус: идея, кода нет. Автор идеи: Антон Советов.

## Проблема

Две консоли с чатами работают над разными задачами в одном проекте.
Они **не знают друг о друге**: каждый правит свои файлы, оба могут
одновременно менять один модуль, оба могут принять несовместимые
решения — и узнать об этом только через конфликт в git или, хуже,
через сломанный тест после слияния.

Сейчас общение идёт через `ai-memory message_send`, но это **ручное**:
человек копирует письмо из одного чата в другой. Это работает, но:

- медленно — человек в цикле;
- неинтерактивно — пока не скопируют, адресат не узнает;
- нет состояния — непонятно, прочитано ли письмо;
- нет координации — нельзя сказать «я сейчас трогаю `wire.c`, не лезь».

## Что нужно

Брокер, который **сам** доставляет сообщения между чатами в одном
проекте, и через который они согласовывают действия.

### Обязательные свойства

| Свойство | Почему |
|---|---|
| **Автодоставка** | адресат узнаёт о сообщении без действий человека |
| **Состояние доставки** | pending / delivered / read / acked |
| **Привязка к проекту** | чаты в разных проектах не мешают друг другу |
| **Адресация** | «всем в проекте» / «конкретному чату» / «кто трогает файл X» |
| **Арбитраж ресурсов** | «я держу `src/wire.c`» — второй чат видит и ждёт |
| **Транспорт-независимость** | Claude Code, Hermes, Codex, любой MCP-клиент |
| **История** | кто что сказал, когда, и чем кончилось |

### Чего быть не должно

- **Не блокировать** чат, если брокер недоступен — деградация в тишину.
- **Не требовать** единого харнеса — протокол, а не плагин.
- **Не хранить секреты** — только координация.

## Архитектура (предварительно)

```
   ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
   │  чат A       │        │  чат B       │        │  чат C       │
   │ Claude Code  │        │ Hermes       │        │ Codex        │
   └──────┬───────┘        └──────┬───────┘        └──────┬───────┘
          │ MCP                    │ MCP                    │ MCP
          └────────────┬───────────┴────────────────────────┘
                       ▼
              ┌─────────────────┐
              │  chat-broker    │   демон, локально
              │  · очереди      │   (Unix socket / TCP)
              │  · арбитраж     │
              │  · журнал       │
              └─────────────────┘
```

### Почему демон, а не файл

Файл не даёт мгновенной доставки и блокировок. Демон даёт.

### Почему MCP

MCP уже поддерживают все нужные харнесы. Не надо писать адаптер под
каждый — брокер отдаёт MCP-сервер, клиент подключает.

## API (черновик)

### Отправка

```
broker_send(to, subject, body, reply_to=?, ttl=?)
  to: "*" | "<session-id>" | "file:<path>" | "tag:<tag>"
```

### Приём

Два режима:

1. **Push** — брокер сам вставляет сообщение в контекст чата, когда тот
   делает следующий запрос к модели. Реализуется через хук
   `UserPromptSubmit` (Claude Code) — брокер отдаёт текст, харнес его
   добавляет.
2. **Pull** — чат сам опрашивает `broker_recv()` в нужный момент.

Push нужен для интерактивности, pull — для надёжности.

### Арбитраж

```
broker_lock(path, ttl_s) -> lock_id
broker_unlock(lock_id)
broker_locks() -> [{path, owner, expires}]
```

Простая блокировка файла с TTL. Не файловая система — брокер держит
состояние. Нужно, чтобы два чата не правили один модуль одновременно.

### Журнал

```
broker_history(since=?, limit=?) -> [{ts, from, to, subject, state}]
```

## Что уже есть на рынке (проверить)

| Что | Отношение к задаче |
|---|---|
| **MCP** | транспорт, но не координация. База, на которой строить |
| **Google A2A** | агент-агент протокол, но про удалённых агентов, не про локальные чаты |
| **ai-memory messaging** | ручная доставка через MCP, наш текущий вариант |
| **tmux / screen** | не про сообщения |
| **Claude Code Agent Teams** | внутри одного харнеса, не между харнесами |
| **File-based inbox** (`.claude/mail/`) | простое, но без автодоставки |

**Вывод:** похожего, что решает именно «две консоли в одном репозитории
сами согласовывают действия», я не нашёл. Ближайшее — A2A, но он про
другое (агенты разных организаций, HTTP, а не локальные сессии).

## Что нужно решить перед началом

1. **Транспорт демона:** Unix socket (Linux/Mac) или TCP (нужен и Windows).
   Наземка на Windows — значит TCP на localhost.
2. **Идентификация чата:** как брокер понимает, какой чат к нему
   подключился? Варианты: PID + cwd, session-id из хука, явный токен.
3. **Push в Claude Code:** какой хук? `UserPromptSubmit` даёт вставить
   текст в промпт, `SessionStart` — в начало сессии.
4. **Хранение:** SQLite (нормально для Windows и Linux) или файлы.
5. **Арбитраж:** блокировки файлов — или сразу через git (`git status`)?
6. **Формат сообщения:** свободный текст или структура (JSON)?

## С чего начать

1. Демон на Python (быстро) или C++ (единый язык с Аэробазис).
2. MCP-сервер с тремя инструментами: `send`, `recv`, `locks`.
3. Хук `UserPromptSubmit` в Claude Code — push.
4. Проверить на двух чатах в одном проекте.

## Открытые вопросы

- Как избежать эха: чат получил сообщение, ответил — и сам получил свой
  ответ как новое сообщение.
- Что делать, если чат занят долгой задачей и не обращается к модели
  часами — сообщение просто ждёт?
- Нужна ли модерация, чтобы два чата не ушли в бесконечную переписку.
- Как связать с `ai-memory`: писать ли в неё копию переписки.
