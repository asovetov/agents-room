# agents-room

Слой координации для ИИ-агентов, которые работают в **разных репозиториях** и
должны договариваться друг с другом: API в одном репозитории, клиенты,
которые его вызывают, — в других, каждый со своими сессиями и часто со своим
харнессом.

Комнаты репозиториев плюс общие комнаты, которые их связывают; присутствие
сессий, лизы на файлы, обнаружение расхождений и адресация по файлу или
тегу — всё поверх MCP. Один статический бинарник, один файл SQLite, без
демона.

Автор идеи: Anton Sovetov. Лицензия: GPLv3, навсегда, не продаётся.

## Какую проблему это решает

Два агента в двух репозиториях не видят друг друга вообще. Агент в `api`
меняет форму ответа; агент в `bot`, в другом чекауте с другим харнессом,
продолжает слать старое поле и падает так, что это выглядит как его
собственный баг. Ни в одном из репозиториев не записано, что другая сторона
существует.

agents-room — то место, где они встречаются. Комната репозитория появляется
сама; общая комната — там, где репозитории сходятся:

```
repo:api ──┐
           ├── shared:storefront
repo:bot ──┘
```

## За минуту

```bash
agents-room join --room repo:api --also storefront --label api --autonomy 2
agents-room send --session $ID --to file:src/api/users.go --subject "нужно поле phone"
agents-room recv --session $ID
agents-room history --room shared:storefront
```

Тело сообщения никогда не едет в сигнале пробуждения. Сигнал — одна строка
о том, что что-то ждёт; агент забирает тело сам. Контекст получателя
остаётся маленьким, а `read` значит, что получатель действительно увидел
содержимое.

## Чего он не делает

- **Не угадывает.** Неизвестный id сессии — ошибка, а не пустой ящик;
  молчащий чат не выдаётся за вышедший; лизу, которую нельзя проверить, он
  не продлевает.
- **Не держит демон.** Если функции нужен демон — это неправильная функция.
- **Не вливает тела сообщений в контекст модели** без спроса.
