# Chat Broker — ТЗ v0.1

Дата: 2026-11-06. Статус: черновик для старта в новом чате.

## Задача одной фразой

Локальный демон, через который два и более чата (разных харнесов) в
одном проекте автоматически обмениваются сообщениями и согласуют доступ
к файлам.

## Границы

**Входит:**
- обмен сообщениями между чатами одного проекта;
- состояние доставки;
- блокировки файлов с TTL;
- журнал;
- MCP-сервер как единственный интерфейс.

**Не входит (пока):**
- обмен между машинами;
- обмен между проектами;
- шифрование (локальный демон, не нужно);
- встраивание в конкретный харнес (только хук, если харнес умеет).

## Модель

```
project        — каталог с .chat-broker/ (маркер)
session        — подключение чата; id выдаёт брокер при connect
message        — {id, from, to, subject, body, state, ts, reply_to}
lock           — {path, owner, expires}
```

### Состояния сообщения

```
pending -> delivered -> read -> acked
                \-> expired (ttl)
```

- `pending` — в очереди получателя;
- `delivered` — доставлено в контекст (push) или прочитано (pull);
- `read` — получатель вызвал `recv`;
- `acked` — получатель явно подтвердил.

## Протокол (MCP tools)

### `broker_connect(project, harness, pid?) -> session_id`

Регистрирует чат. Брокер возвращает `session_id`. Вызывается на старте.

### `broker_send(to, subject, body, reply_to?, ttl_s?) -> message_id`

`to` — селектор:
- `"*"` — всем в проекте, кроме себя;
- `"<session_id>"` — конкретному;
- `"file:<path>"` — всем, кто держит блокировку на путь;
- `"tag:<tag>"` — по метке, которую чат указал при `connect`.

### `broker_recv(wait_s?) -> [messages]`

Забирает `pending`. `wait_s > 0` — long-poll.

### `broker_ack(message_id)`

### `broker_lock(path, ttl_s) -> {ok, holder?}`

Если путь занят — `ok=false` и `holder` (кто держит).

### `broker_unlock(path)`

### `broker_locks() -> [locks]`

### `broker_history(since?, limit?) -> [messages]`

## Push-доставка

Харнес, который умеет хуки, регистрирует:

- **Claude Code:** `UserPromptSubmit` — брокер возвращает текст новых
  сообщений, харнес добавляет его к промпту.
- **SessionStart** — приветствие и список активных чатов.

Если хук недоступен — чат работает в pull-режиме.

## Хранение

SQLite в `.chat-broker/broker.db`. Причины:
- один файл, работает на Linux и Windows;
- транзакции — не нужны блокировки поверх;
- легко читать журнал снаружи.

Схема:

```sql
sessions(id TEXT PRIMARY KEY, project TEXT, harness TEXT, pid INT,
         tags TEXT, connected_at INT, last_seen INT)
messages(id TEXT PRIMARY KEY, project TEXT, sender TEXT, recipient TEXT,
         subject TEXT, body TEXT, state TEXT, reply_to TEXT,
         created_at INT, expires_at INT)
locks(path TEXT PRIMARY KEY, project TEXT, owner TEXT, expires_at INT)
```

## Демон

- Один процесс на пользователя, слушает `127.0.0.1:<port>`.
- Порт в `.chat-broker/port` (создаёт сам при старте).
- Автозапуск: `broker-mcp` при первом подключении поднимает демон,
  если не запущен.

**Почему TCP, а не Unix socket:** нужен Windows (клиент).

## MCP-сервер

Отдельный процесс `broker-mcp`, который говорит с демоном по TCP и
отдаёт MCP-инструменты. Клиент подключает его как обычный MCP-сервер:

```json
{"mcpServers": {"chat-broker": {"command": "broker-mcp",
                                "args": ["--project", "/path/to/project"]}}}
```

## Защита от проблем

| Проблема | Решение |
|---|---|
| Бесконечная переписка двух чатов | лимит `max_exchanges` на пару за час, потом блок |
| Эхо собственных сообщений | `sender` не получает свои |
| Чат ушёл, блокировка осталась | TTL на всех блокировках |
| Демон упал | чаты деградируют в тишину, не падают |
| Два проекта с одинаковым путём | `project` — абсолютный путь + хеш |

## Тесты

1. Два клиента, сообщение от A к B доходит.
2. `*` не возвращается отправителю.
3. Блокировка: второй получает `ok=false` с владельцем.
4. TTL блокировки истекает.
5. Журнал отдаёт историю.
6. Демон перезапущен — состояние сохранено.
